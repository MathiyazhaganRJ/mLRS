2. STM32F103CB (DIY E28 Board01) Porting to mLRS v1.4

The custom DIY E28 Board01 transmitter and receiver hardware is built around the STM32F103CB (128 KB Flash, 20 KB RAM) paired with the Semtech SX1280 2.4GHz RF transceiver via SPI1.

Key Architectural Fixes Implemented for v1.4

  1. Transition to DEVICE_HAS_COM_ON_SERIAL:
    In mLRS v1.2, boards with single shared UART for both MAVLink telemetry and interactive CLI configuration used DEVICE_HAS_SERIAL_OR_COM. In v1.4, this was refactored: defining DEVICE_HAS_COM_ON_SERIAL informs hal.h to cleanly multiplex interactive CLI and high-speed telemetry on UART2 (PA2/PA3) without requiring a physical UARTC hardware peripheral.
  2. Debounced Hardware Boot Mode Selector (ser_or_com_init):
    On DIY Board01, PB11 is used by the SX1280 interrupt (SX_DIO1), preventing UART3 from operating as a dedicated CLI port. A debounced sampler was implemented in tx-hal-diy-e28-board01-rj-f103cb.h: 
    bool ser_or_com_init(void) // return true if is_serial (MAVLink), false if CLI
{
  button_init();
  uint8_t cnt = 0;
  for (uint8_t i = 0; i < 16; i++) {
    if (gpio_read_activelow(BUTTON)) cnt++;
    delay_ms(1);
  }
  return (cnt > 12) ? false : true;
}
    • Normal Boot (Button released): Boots straight into high-speed MAVLink telemetry serial port for Mission Planner / QGroundControl.
    • Configuration Boot (Hold Bind button PC13 at power-on): Boots into interactive CLI terminal mode for parameters and calibration.
  3. Centralized Systick Timing:
    Removed local SYSTICK_TIMESTEP and SYSTICK_DELAY_MS macro definitions from target HAL files. mLRS v1.4 handles systick timing centrally in Common/hal/timer.h.
  4. Windows Toolchain Space-in-Path Correction:
    In tools/run_make_firmwares.py, calling external tools (such as C:\Program Files (x86)\Arm GNU Toolchain...) via os.system() caused Windows cmd.exe to strip outer quotes. The build script was patched to prepend GCC_DIR into os.environ["PATH"] and invoke bare tool names (arm-none-eabi-gcc, size, objcopy), ensuring 100% reliable builds on Windows.

3. Raspberry Pi RP2040 & RP2350 Architecture & Build Guide

RP2040 (Raspberry Pi Pico) and RP2350 (Raspberry Pi Pico 2) targets bypass STM32CubeIDE and compile using PlatformIO with the optimized Arduino-Pico core by Earle Philhower.

Dual-Core Distribution

Core 0: Executes the real-time RF protocol loop, Semtech SPI driver, FHSS pseudo-random frequency hopping state machine, and packet telemetry engine.

Core 1: Dedicated entirely to high-throughput USB CDC ACM emulation, continuous serial ring buffers, and peripheral background transfers.

PIO State Machine Acceleration

can2040 Driver: A bit-exact CAN 2.0B controller synthesized completely inside the RP2040 Programmable I/O (PIO). Eliminates external CAN controller ICs (e.g. MCP2515)—only a 3.3V transceiver PHY is required.

JR Bay Pin 5: Single-wire bidirectional half-duplex UART implemented on PIO with sub-microsecond precision.

4. Evaluation: STM32F412REY6TR Feasibility

The STM32F412REY6TR is an ultra-compact WLCSP-64 packaged MCU (Cortex-M4 @ 100MHz, 512KB Flash, 256KB RAM, 5× SPI, 4× USART, 2× bxCAN).

Hardware Capability Verdict

EXCELLENT HARDWARE

The chip has over 5× the required Flash memory, 12× the required RAM, hardware FPU, dual bxCAN controllers, and 50 MHz SPI buses. It is exceptionally well-suited for high-density miniature avionics.

mLRS Codebase Compatibility

NOT SUPPORTED OUT-OF-THE-BOX

mLRS uses OlliW's stripped-down stm32ll-lib. It currently has drivers for F1, F3, G4, L4, WL, and F0, but no STM32F4 support exists in the repository.

Work Required to Port mLRS to STM32F412

  1. Import STM32CubeF4 LL driver headers (stm32f4xx_ll_gpio.h, _rcc.h, _usart.h, _spi.h, _tim.h).
  2. Add F4 bootloader entry vector (0x1FFF0000) and clock switching in stdstm32-mcu.h.
  3. Create target class cTargetF4 in tools/run_make_firmwares.py.
  4. Provide startup assembly (startup_stm32f412rx.s) and linker script (STM32F412RETX_FLASH.ld).

The Critical 128 KB Flash Bottleneck in AP_Periph ArduPilot AP_Periph firmware includes a CAN bootloader, DroneCAN protocol stack, parameter storage, and sensor drivers (GPS, Compass, Baro, Battery Monitor, Airspeed, MSP). A complete build typically occupies 130 KB to 180 KB. On a 128 KB chip like the STM32G431KBU6, multi-sensor builds will fail with flash overflow errors unless features are manually stripped out in hwdef.dat. The 256 KB Flash on the L431 completely eliminates this issue.

6. In-Depth Evaluation: STM32L431CCU6 (Robu.in)

The STM32L431CCU6 available domestically in India via Robu.in represents the optimal solution for custom hardware fabrication.

Key Specifications

  • Silicon Core: ARM Cortex-M4 with single-precision hardware FPU @ 80 MHz.
  • Flash Memory: 256 Kbytes (ample headroom for both mLRS and AP_Periph).
  • SRAM: 64 Kbytes.
  • Package: UFQFPN-48 (7 × 7 mm, 0.5 mm pitch).
  • Peripherals: 1× bxCAN (CAN 2.0B Active), 3× SPI, 3× I2C, 4× USART/LPUART, 16× DMA channels.

Why the 48-Pin Package (`CCU6`) Outperforms the 32-Pin (`KCU6`)

The CCU6 provides 16 additional GPIO pins while maintaining a miniature 7×7 mm footprint. This solves pin contention between SPI, CAN, I2C, and UART peripherals:

The "Zero Code Change" Reality

AP_Periph: 100% Zero Code Change

Because the 48-pin CCU6 contains all 32 pins of the KCU6 in the exact same peripheral layout, wiring the CAN transceiver to PB8/PB9 makes the board 100% plug-and-play compatible with official MatekL431 binaries.

You can download pre-compiled AP_Periph.bin files directly from firmware.ardupilot.org without compiling source code.

mLRS: Zero Core Changes + 1 HAL File

The main mLRS engine (mlrs-rx.cpp, mlrs-tx.cpp, SX1280 driver, crypto, FHSS) requires zero modifications. The STM32L4 architecture is already verified.

Because every custom PCB routes RF SPI and control lines to specific pins, you simply create one pinout definition header (e.g. rx-hal-diy-l431cc.h) mapping your chosen pins. It compiles in seconds using the existing cTargetL4 compiler rules.
